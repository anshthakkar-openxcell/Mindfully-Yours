## Tier 6 — Confirmed wrong in the source material (not a discrepancy between PDFs — an outright error)

### 28. Sarvam does not offer an embeddings model — the whole KB's vector search needed a different vendor
All 3 architecture PDFs and `APPROACH.md` name **Sarvam** as the embeddings vendor (see [03_TECH_STACK.md](03_TECH_STACK.md) §3). This is confirmed wrong, not unconfirmed: checked directly against Sarvam's live model list and API reference (Sept 2026) — Sarvam has speech-to-text, text-to-speech, translation, and chat/LLM models, but no `/embeddings` endpoint or embeddings model of any kind. The codebase's own `app/providers/embeddings/sarvam_embeddings.py` had been a placeholder calling a made-up endpoint (`/v1/embeddings`, model name `"sarvam-embed"`) that never corresponded to a real product — it has been deleted and replaced with a real, working `OpenAIEmbeddingProvider` (`text-embedding-3-small`, already the documented fallback/benchmark option, requesting `dimensions=1024` to match the existing schema). **This is a genuine vendor substitution, not a config tweak — it needs the client's written sign-off per [12_SECURITY_COMPLIANCE_DPDP.md](12_SECURITY_COMPLIANCE_DPDP.md) Clause 2.8 before any real user data is embedded with it.** Fine to use as-is for dev/test.

**Follow-up, found by actually live-testing the swap against real messages (2026-09-28):** the two confidence thresholds in `.env` (`REDFLAG_MATCH_THRESHOLD=0.55`, `RETRIEVAL_CONFIDENCE_THRESHOLD=0.75`) were never based on real data — they were guessed for Sarvam's embedding space, which turned out not to exist. Tested against OpenAI's real embeddings: genuine suicidal-ideation paraphrases (not verbatim trigger phrases) scored 0.44–0.60 similarity against the correct red flag, and a correct self-care-tool match scored 0.33 — both **below** the old thresholds, meaning the safety interlock and self-care recommendation would have silently failed to fire on real danger signals and valid matches. Recalibrated to `REDFLAG_MATCH_THRESHOLD=0.44` and `RETRIEVAL_CONFIDENCE_THRESHOLD=0.30` — re-tested afterward and both now correctly fire, with no false positives on 3 safe control messages. **These new values are a data-informed starting point from a small manual test (~9 messages total), not a validated threshold** — a real validation set is still needed before production, same as the already-deferred validation gate.

**A second, independent bug found during the same testing pass:** `app/ingestion/parsers/red_flags.py` looked up the Bot Script column using `"Bot Script (YOU write -- verbatim)"` (two hyphens), but the real CSV header uses a genuine em-dash (`—`) in that phrase. The mismatched dict key silently returned `None` for every row, not just the 4 documented ones (RF-028–031) — including RF-018 and RF-019 (passive/active suicidal ideation), the most safety-critical flags in the table. This meant the safety interlock would trigger correctly but reply with the generic fallback text instead of the clinically-written verbatim script for 27 of 31 flags. Fixed by finding the column by prefix instead of an exact literal; re-ingested and confirmed all 31 flags now resolve correctly (only RF-028–031 genuinely lack a script in the source data, exactly as originally documented in [05_KNOWLEDGE_BASE_DEEP_DIVE.md](05_KNOWLEDGE_BASE_DEEP_DIVE.md) §5).

**A concrete, reproducible false-positive found via the test harness (2026-09-29):** ordinary relationship language falsely triggered the interlock at the current threshold. Tested 4 variations of "wanting to leave a partner" — 3 of 4 scored above `REDFLAG_MATCH_THRESHOLD=0.44` against RF-028 ("Suspected of violence/unsafe environment") or RF-025 (suicidal/self-harm), despite containing zero actual danger content:
- *"i wanna leave my partner"* → RF-028, similarity 0.459 → **falsely triggered**
- *"i want to leave my partner"* → RF-028, similarity 0.462 → **falsely triggered**
- *"i think i want to break up with my partner"* → RF-025, similarity 0.451 → **falsely triggered**
- *"my partner and i are not working out anymore"* → RF-028, similarity 0.409 → safe, but barely

Root cause: every one of RF-028's example phrases mentions "partner," so the embedding model clusters *any* short, emotional partner-related sentence nearby — real danger content isn't what's being detected, topic overlap is.

**FIXED, 2026-09-29 (`app/safety/interlock.py`'s `SOFT_ZONE_ELIGIBLE_FLAGS`):** raising the global threshold was rejected for the reason above — it risks missing genuine partner-abuse disclosures that use nearly identical wording. Instead, RF-028 specifically (never the suicide/self-harm flags) now has a two-tier response: a match at/above `REDFLAG_SOFT_ZONE_THRESHOLD=0.55` still hard-escalates exactly as before; a match between `REDFLAG_MATCH_THRESHOLD` (0.44) and 0.55 no longer fires the crisis script at all — instead it fetches a real, doctor-written question from `kb_clarification_phrases`'s "Clarifying Relationships" category (e.g. "Can you tell me more about that relationship?") and has the LLM weave it naturally into an ordinary, warm reply. Live-tested end-to-end: "i wanna leave my partner" now gets a normal supportive conversational response with a genuine follow-up question, not a crisis-counsellor redirect, while a real RF-018/019/025 disclosure still gets the full hard escalation unconditionally (see the item directly below — those flags were deliberately excluded from this softer treatment, and needed the opposite fix instead).

**A second, more serious problem found while regression-testing the fix above:** the *opposite* failure — real suicidal-ideation disclosures being *missed* — turned out to already be happening. Testing canonical phrasings directly against `kb_red_flags`:
- *"i want to kill myself"* → best match RF-019, similarity 0.392 → **below `REDFLAG_MATCH_THRESHOLD=0.44`, missed**
- *"i want to end my life"* → best match RF-019, similarity 0.394 → **missed**
- *"i've been thinking about suicide"* → single globally-nearest flag was RF-020 ("Psychotic Feature") at 0.395, not a suicide flag at all — RF-019/RF-018 sat right behind it at ~0.38-0.39 but were never even considered, because the old code only ever looked at the single nearest match across all 31 flags, not the runner-up candidates. **Missed.**
- *"i have a plan to kill myself tonight"* → RF-019, similarity 0.557 → correctly triggered (the only tested phrasing explicit enough to already work)

Two compounding bugs, both fixed in the same `app/safety/interlock.py` change: (1) the interlock only ever fetched the single globally-nearest red flag, so a suicide flag sitting in 2nd or 3rd place was never checked at all; (2) the 0.44 threshold itself is too high for how these flags' trigger phrases actually sit in embedding space. Fix: `CRITICAL_SELF_HARM_FLAGS = {"RF-018", "RF-019"}` are now checked among the top 15 nearest candidates (not just the single best), against a separate, lower `REDFLAG_CRITICAL_THRESHOLD=0.36`.

**This threshold is a deliberately imperfect, evidence-based compromise, not a clean fix** — live testing found real disclosures (0.366-0.409 similarity against RF-018/RF-019) and ordinary messages ("i had a fight with my mom and i feel terrible" scored only 0.19-0.29 against these two flags specifically) separate cleanly. 0.36 was chosen to sit on the sensitive side of the small remaining margin: it correctly catches every real disclosure phrasing tested so far. That's intentional — this project's own stated principle is that a missed disclosure is the one failure mode that must never happen, while an unnecessary "are you safe right now" check-in is a mild, tolerable cost. **Still needs**: a real validation dataset (hundreds of labeled real/decoy examples, clinical-team reviewed) — a handful of source phrases per flag is not enough to pin down a stable boundary long-term.

**RF-025 was originally included in `CRITICAL_SELF_HARM_FLAGS` too, then removed after a third round of live testing (2026-09-29) found via the test harness UI** that it caused its own, worse false-positive class: ordinary anger directed at *other* people, with zero self-harm content, falsely hard-escalated as RF-025 ("suicidal/self-mutilating behaviours"):
- *"i fought with my best friend and i feel like hitting him"* → RF-025, similarity 0.480 → **falsely triggered**
- *"i had a fight with my best friend"* → RF-025, similarity 0.406 → **falsely triggered**

Root cause, found by reading RF-025's actual source data: one of its 5 `trigger_phrases` is literally *"banging my head/cutting my wrist/slamming my fist in the wall"* — the "slamming my fist in the wall" clause pulls RF-025's embedding toward generic fist/hitting/physical vocabulary, so it matches anger-at-someone-else language even though that has nothing to do with self-harm. This wasn't limited to the new sensitive top-K check either — "...feel like hitting him" (0.48) clears even the *original*, unmodified `REDFLAG_MATCH_THRESHOLD=0.44` on its own, via the plain top-1 path. Confirmed this isn't just a threshold problem: RF-001 ("aggressive behaviour", the semantically correct flag for anger-at-others) does *not* fire on any of these phrases either (0.36-0.41, below its own bar) — meaning these messages genuinely aren't red-flag material at all; RF-025 alone is over-broad.

**FIXED**: RF-025 removed from `CRITICAL_SELF_HARM_FLAGS` (not needed there — see below), and given its own stricter, flag-specific bar via a new `NOISY_FLAG_THRESHOLDS = {"RF-025": 0.50}` used in place of the generic threshold whenever RF-025 is the top-1 match. 0.50 was chosen because every tested anger/conflict false positive topped out at 0.48, while most real self-harm disclosures scored 0.57-0.64. **One acknowledged residual gap**: "i've been cutting myself lately" scored only 0.466 against RF-025 — below the new 0.50 bar, so RF-025 alone would miss it.
