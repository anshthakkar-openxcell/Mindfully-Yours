How a reply is produced

The whole flow in plain language: what happens to a user's message, where the data lives, how the reply is chosen, and why we built it this way.

The idea in short

  1. The therapists' conversations are the product. A reply should come from them first. The LLM is a helper that rewords, and a last resort.
  2. One "meaning vector" per message. The message is turned into a list of numbers that captures its meaning. Every search reuses that one vector.
  3. Safety is checked first, always. A red flag gives the approved script, word for word. The LLM is never involved.
  4. Then we search the therapist conversations by meaning. Very close: send the therapist's reply as written. Fairly close: the LLM rewords a few close examples, and a check stops it adding anything. Not close: ask a therapist-written question, and only then use the LLM.
  5. One PostgreSQL does two jobs. The tables ("RDS") and the vector search are the same database. Redis only holds short-lived memory.
  6. Everything is explainable and adjustable. Each reply is logged with its source, every cut-off is a config setting, and the library grows by adding approved rows. No retraining and no deploy.

The pieces and where they sit

PostgreSQL (the RDS) + pgvector

One database. Normal columns hold text, rules and scripts. A vector column on the same row holds the meaning vector, and an index makes finding the nearest vectors fast. One query returns the nearest rows and their text, so there is nothing to keep in sync.

Redis

Short-lived memory only: the conversation so far (6 hours) and a 24-hour cache of repeated replies. Nothing here is the source of truth.

Outside AI services

OpenAI makes the meaning vectors (embeddings). Sarvam does the language model, speech, and translation. All sit behind adapters so they can be swapped.

THE FLOW

One message, start to finish: part A

  • One embedding per message. It is the slowest step (about 0.3 to 1.3 s, sometimes 2 to 3 s). Every search reuses it. A second one in sequence would break the time budget.
  • The therapist search starts early and runs in the background on its own database session, while triage and the safety check run. When we need the answer it has already finished.
  • Safety can cancel everything. If a red flag matches, the therapist search is dropped and the approved script is sent. If the embedding or the safety check itself fails, the reply is a safe "let me connect you with someone".

THE FLOW

One message, start to finish: part B

  • Order matters: a strong therapist match is sent before the cache is even looked at. A partial match checks the cache first. A therapist reply beats a cached AI reply, and a cached reply beats calling the AI again.
  • The clarifying question is only used when nothing at all grounds the reply, the message has at least 4 words, and we have not just asked one (the limit is 1 in a row).
  • Last step: memory is updated, the AI reply (not therapist replies) is cached, and one audit row records which path answered.

Index gotcha: the fast index only applies to rows that are approved and eligible, so the query must be written with plain boolean columns. SQLAlchemy's .is_(True) becomes "IS true", which Postgres cannot match to the index, and it silently scans every row. After changing that query, run EXPLAIN and look for the index name.

The three kinds of reply

1 Strong: the therapist's reply, as written

The reply stored for the nearest conversation is sent unchanged. No LLM call, so it is the fastest and lowest-risk path. It gets slightly faster and cheaper as the library grows.

Logged as therapist_verbatim

2 Partial: the LLM rewords, but cannot invent

A small prompt shows up to 3 close therapist examples (someone said X, the therapist replied Y) and says: write one reply using only the ideas and wording already in them; add no advice, numbers or links.

The output is held back and checked: no new numbers or links, about the same length, and most of its words come from the therapists' text. If it fails, the therapist's original is sent. If the LLM errors, same fallback.

Logged as therapist_adapted / therapist_verbatim_fallback

3 None: ask, then the LLM

First, what can ground the reply (in this order): a soft-concern follow-up, the booking nudge, Tier 1 self-care advice, or probing guidance for the likely pattern.

If nothing grounds it, ask the nearest generic therapist clarifying question (once). Otherwise the LLM answers with the persona, a checklist of what to quietly notice, the last 6 turns and that one piece of grounding.

Logged as therapist_clarify / rag_retrieval

What the guard does and does not do

It is instant (no second model call), so it adds no delay. It catches drift, padding and added numbers or links. It does not prove the meaning is identical, and for non-English replies only the number, link and length checks apply. Setting CURATED_PARTIAL_MODE=verbatim skips the LLM for partial matches.

Where the LLM never goes

It never decides whether something is a crisis, never edits a safety script, and never adds clinical advice to a matched therapist reply. For fully AI-written replies the output check today only logs a problem; it does not block.

Safety: the part that must never regress

  • Runs first, every message. Even when a cached reply exists. Nothing that writes a reply may be placed before it.
  • Matching is by meaning, the answer is a stored script. Embeddings catch indirect wording; the reply is the clinician-approved text, word for word.
  • Thresholds are deliberately permissive: a false alarm costs a moment of caution; a miss costs a danger signal. General cut-off 0.44. For the two suicide flags the top 15 candidates are checked at 0.36.
  • Fails safe, upward. If the embedding or the safety check fails: "let me connect you with someone". Never a silent continue.
  • No script, no LLM. Four red flags have no approved script yet; they raise a human alert instead.

The soft zone (a gentler path for two flags only)

For RF-028 and RF-007 a match between 0.44 and 0.55 gets a gentle follow-up instead of a crisis script. At 0.55 or above they still escalate fully. RF-007 (startle, hyperarousal) was added because everyday worry scored 0.39 to 0.44 against it while its real examples scored 0.50 to 0.69.

Suicide and self-harm flags are never allowed in the soft zone. A unit test fails if one is added.

Before touching any of this

Change thresholds only with clinician sign-off, and run the red-flag test messages before and after. The kill switch for the new therapist-first behaviour is CURATED_MATCH_ENABLED=false; it does not touch safety.

How data gets in, and how to add more

Rows that are stored but never searched

  • Crisis / Tier 3 conversations: the safety path owns these
  • Content on governance hold
  • Unfinished text: placeholders and drafting notes
  • Possible leaked headings inside a reply
  • Very short user messages (under 4 words)

Re-running is safe: each row is keyed by a hash of its text, so ingestion adds or updates and never duplicates. Approval is never reset by a re-run.

Runbook: add or fix therapist content

  1. Put the .docx in the source folder (User: and AI: lines).
  2. Run ingest-therapist-turns --dry-run and read the held counts.
  3. Run it for real (add --approve-eligible when ready).
  4. Pre-translate fixed replies with translate-kb.
  5. Check with scripts/try_turn.py 'a message'.
  6. Bad row? update kb_therapist_turns set approved=false where id=...

Other languages, and why this design

Hindi, Hinglish and mixed messages

The safety rules and the therapist library are English. So a non-English message is translated to English first (Sarvam, about 0.7 s) and the whole pipeline runs on the English text. Going out, fixed replies come from a pre-translated table (instant); AI-written replies are written directly in the user's language.

Watch out: translation can soften an idiom; the translated safety scripts are machine translations awaiting review; and the translation service is rate limited (about 100 calls a minute), which caps live non-English users.

What this design gives the AI

  1. A narrow job: reword given examples, which models do reliably.
  2. Grounding in real expert wording, not a persona paragraph.
  3. Contained errors: safety is independent, a bad reword falls back to the original, an LLM outage still serves a therapist reply.
  4. Every reply explainable by source and row.
  5. A built-in improvement loop: add rows, quality rises immediately.

Debugging, settings, and where the code is

Why did it say that?

  1. Run scripts/try_turn.py 'message': it prints the source, the therapist row ids, the similarity and the timings.
  2. Or look in turn_audit_log: served_from, retrieved_chunk_ids (therapist_turn:id), latency_ms.
  3. Fetch the row: select * from kb_therapist_turns where id = ...
  4. Share of therapist-made replies: select served_from, count(*) from turn_audit_log group by 1

Settings (.env)

  • CURATED_MATCH_ENABLED kill switch
  • CURATED_STRONG_SIMILARITY 0.85
  • CURATED_PARTIAL_SIMILARITY 0.62
  • CURATED_NON_OPENING_MARGIN 0.05
  • CURATED_PARTIAL_MODE rephrase or verbatim
  • CURATED_MAX_EXAMPLES 3
  • CURATED_CLARIFY_LIMIT 1
  • REDFLAG_* safety: clinician sign-off only
  • TRANSLATION_ENABLED

Honest weaknesses of the design

  • Matching uses one message, so context-dependent replies can match badly.
  • Coverage-bound: a thin library means many 'none' results.
  • Cut-offs are not yet validated. Strong is set high on purpose.
  • Verbatim replies can feel repetitive in a long chat.
  • Approved is not clinically reviewed. Casual companion-style chats are in the library and could match a distressed user if the cut-offs are loose.
