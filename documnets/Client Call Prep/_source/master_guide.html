Part A - The 5-minute warm-up

A1. The 60-second explanation (say this first)

Say: "The product's value is the therapists' expertise, so a reply should come from their conversations, not from an LLM's general knowledge. When a user writes something, we turn it into a meaning-vector once. First, an independent safety check compares it to the doctors' red-flag list and, if it matches, sends the doctors' approved script word for word - the LLM is never involved. If it is safe, we search the therapists' own conversations by meaning. A very close match is sent exactly as written. A partial match is lightly reworded by the LLM, but only using the therapists' own words, and we check it did not add anything. If nothing matches, we ask a therapist-written clarifying question first, and only then let the LLM answer - grounded in the therapists' self-care material. In the background we keep a running severity score across the whole conversation so we can move someone from self-care (Tier 1) to 'consider a professional' (Tier 2) carefully, while genuine crisis (Tier 3) is handled only by the instant red-flag check. Everything is logged with where the reply came from."

A2. The six ideas everything else hangs on

#IdeaOne-line meaning
1Grounded, not inventedThe AI may not invent mental-health advice. Content comes from the client's approved material; the LLM mostly phrases.
2Safety lives outside the AIA rule/similarity check against the red-flag list runs on every turn, before any reply is written. It returns the doctors' exact script. The LLM never decides safety.
3Therapist-firstClient requirement: if a similar therapist conversation exists, the reply is curated from it. LLM is demoted to phraser and last resort.
4Stay human on the outsideNo quizzes or forms. All severity assessment happens silently from ordinary conversation.
5Match by meaning, not keywordsText is converted to embeddings (vectors). "I wish I could just disappear" lands near "I don't want to be here" although no words are shared.
6Everything is explainableEvery turn writes an audit row: where the reply came from (served_from), which therapist row, similarity, timings, tier score.

A5. If you only remember five sentences

  1. Safety first, always, on every message, and it returns the doctors' exact words.
  2. Then we look for the therapists' own reply by meaning; strong match is sent unchanged, partial is reworded under a check, none leads to a therapist clarifying question.
  3. The LLM is a phraser and a last resort, never the author of clinical content on a matched case.
  4. Tier 3 means crisis and only the red-flag check can produce it; the running score can only ever reach Tier 2, and even then booking is only suggested after a stricter confidence gate.
  5. All thresholds are provisional starting points; calibrating them with therapist-labelled data is the single most valuable next piece of work, and we say so openly.

Part C - The ingestion pipeline (client files → searchable knowledge base)

Ingestion is offline: it runs when files arrive or change, never while a user is waiting, so it may take time and be careful. Governing principle: retrieval can never be better than what ingestion gave it.

C1. The pipeline, step by step

1. Intake. Client sends CSV / Excel exports / Word files (some password-protected; one Word file built entirely from drawing text-boxes).
▼
2. Structure-aware parsing. One dedicated parser per file type (app/ingestion/parsers/, ~20 parsers). No AI decides where to split - the client's own rows / headings / "User:/AI:" lines are the boundaries.
▼
3. Cleaning & quality gates. Remove template-instruction rows, forward-fill group labels, fix encoding (cp1252), normalise IDs; hold back anything unfinished or sensitive (stored, but marked not searchable).
▼
4. Embedding. Only specific fields (never whole records) are converted to 1024-number vectors with OpenAI text-embedding-3-small, in batches of 64.
▼
5. Store. One PostgreSQL database with the pgvector extension: normal columns + the vector on the same row; HNSW indexes for fast nearest-neighbour search.
▼
6. Approve. Therapist rows default to approved = false; they are served only after approval (--approve-eligible or a per-row update). Bad row? approved=false - instant, no deploy.
▼
7. Pre-translate. translate-kb translates fixed replies into Hindi and Hinglish offline so non-English replies are instant.
▼
8. Spot-check. scripts/try_turn.py "message" runs the real pipeline and prints the source, ids, similarity and timings.

C4. Chunking - "one row = one chunk"

For every file received so far the client's own structure is already the right chunk: one spreadsheet row, one paragraph under a heading, one (user turn → therapist turn) pair. No AI is used to chunk. Fixed-size or similarity-based chunking would cut a clinical idea in half; a clinician-structured file does not need it.

Design vs built. The original design (doc 07) also describes an LLM "chunk-boundary refiner" for future flowing prose, with ~10-15% overlap. That step is not built because nothing received so far needed it. Say: "reserved for unstructured Phase III/IV prose, if it arrives." Similarly the original design said Sarvam embeddings; see Q&A (Sarvam has no embeddings API).

C5. The therapist-conversation parser in detail (most likely to be probed)

  • Speaker detection: a line starting User: / Client: / Parent: / Female: is the user side; AI: / AI Companion: / Al: / A: is the AI side (all real variants found in the source, including the typo "Al:"). Consecutive lines by one speaker merge into one turn.
  • Conversation boundaries: any non-dialogue line (heading/scenario title). A bullet/list line directly after an AI turn continues that turn (tip lists) - except numbered lines that look like the next scenario's heading (e.g. "38. User is upset..."), which would otherwise be spoken to a real user.
  • "Initiate crisis protocol" lines are outcomes of the conversation before them. (Bug found on real data: attaching them to the next conversation wrongly held unrelated topics. Fixed.)
  • Each pair (user turn → AI reply) becomes a row; prior_context keeps up to 2 earlier exchanges for display/review; is_opening marks first-turn replies (635+ of them, 777 incl. drop 2).
  • Idempotency: content_hash = sha256(normalised user text + reply text). Re-ingestion is an upsert; if a parser fix changes a reply, the loader prunes stale rows from the files just re-parsed.

C6. Data-hygiene facts about the client files (so nothing surprises you)

  • Raw CSVs are Windows-1252, not UTF-8; each is a "form template" export (title row, purpose row, instruction rows, then the real header) padded with hundreds of blank rows.
  • Group labels are written once and left blank below - must be forward-filled or data silently disappears.
  • Signal/EM/PHYS codes appear in at least 5 formats (SIG: 001, SIG002-003, SIG-168, unpadded...) - everything is normalised.
  • PHSY- typo for 4 PHYS rows; Sig-285 casing; RULE-/Rule- casing switch.
  • Three emotion lists (19 / 9 / 11) and three severity vocabularies (Tier 1-3, Layer I-IV, Mild-Crisis) do not reconcile - the client must decide (Part G).

Part D - The knowledge base in the database, and how signals work

D1. One database does both jobs (the "RDS vs vector DB" question)

Say: "There is a single PostgreSQL. Ordinary columns hold the text, rules and scripts; a vector(1024) column on the same row holds the meaning vector, and an HNSW index makes nearest-neighbour search fast. One SQL query returns the nearest rows and their text, so there is no second system to keep in sync, secure or pay for. At about 14,000 searchable rows, pgvector is more than enough. We would revisit Qdrant at millions of vectors."

Redis (not Postgres) holds short-lived state: the session (6-hour inactivity TTL) and the exact-reply cache (24 h).

D3. Embeddings and similarity in plain terms

  • An embedding turns a sentence into 1024 numbers that capture its meaning. Similar meanings give nearby vectors.
  • Similarity everywhere = 1 - cosine distance. Typical: same sentence 1.00; good paraphrase 0.65-0.85; related topic ~0.55-0.65; unrelated ≤ 0.5. These are narrower bands than people expect, which is why thresholds must be calibrated, not guessed.
  • One embedding per turn, reused by safety, triage, tier scoring, therapist match and self-care search. It is the slowest step (0.3-1.3 s typical, occasional 2-3 s spikes), so adding a second sequential call would break the 1.5-2.5 s budget.
  • Model: OpenAI text-embedding-3-small with dimensions=1024. This replaced the planned Sarvam embeddings because Sarvam has no embeddings API (checked against their live model list). It needs the client's written sign-off before real user data is embedded with it (DPDP clause 2.8 in the project notes).

Live tests showed a benign message scoring 0.488 against "Hypomania" while a genuinely symptom-bearing message scored 0.479 against its own correct signal. That is why signals accumulate across the conversation, why only new signals add points, why a per-turn cap exists, and why no single triage match can decide anything.

D5. "How does the AI understand the signals?"

Short version: the AI does not "understand" signals - the code does, and the AI is told what to ask.

  1. Recognition is vector matching (above) against the doctors' own phrasings - no LLM.
  2. Meaning is added by the doctors' data: each signal carries a severity (1-3), a category, linked disorders and a red-flag yes/no; each symptom links to signals; each pattern carries "when to keep probing" text.
  3. The LLM never sees raw signal codes or diagnoses. It receives gated guidance: e.g. "naturally ask about how long this has been going on" or the pattern's doctor-written probing instruction - an instruction for what to ask next, never "the user may have disorder X".
  4. The Clinical Markers checklist (10 items) is in the full LLM prompt so the model quietly notices speech, reality testing, thought content etc.; but it cannot change tier or safety.
  5. Two yes/no facts are read by a small LLM call, not by keywords: "has the user said how long?" and "has the user said it affects daily life?" - with an exact supporting quote required. Fails closed (treated as "not yet confirmed").

D6. The A1 + A2 + C11 enrichment (offline join)

Each signal-level record was enriched once, offline, with cross-references from other sheets so no live join is needed: A1 signals get their linked routing rules (matched_rules); A2 symptoms get linked signal concepts, any_linked_red_flag, max_linked_severity. Parsing the messy "Maps to Signal IDs" column handles comma lists, hyphen ranges (SIG-041-043), word ranges (SIG-085 to 093) and free text (no match - a valid result).

Limit to state yourself: only 25 of 285 signals have an auto-matched routing rule, because most C11 rules use range/combination logic ("SIG 001-017 minus 002-003") that single-number matching cannot expand. Offer the client a choice: they rewrite those ~41 rules with explicit signal lists, or we build a smarter range parser.

Why this order (the invariants - say these if challenged on safety)

  • Therapist lookup runs in the background with its own DB session (one async session cannot run two queries at once) so it finishes while triage and the interlock run. Measured wait: ~0.001-0.002 ms.
  • A strong therapist match beats a cached LLM reply; a cached reply beats re-running the LLM.
  • LLM failure never costs the user a reply on the partial path - the therapist's original is sent.
  • Voice barge-in: interrupted turns still save state and audit (*_interrupted) and are never cached.

E3. The partial path: the LLM may reword, not invent

The LLM sees a small prompt: persona + language line + last ≤ 6 turns + up to 3 "when someone said X, the therapist replied Y" examples, with the instruction: "use ONLY the ideas, wording and questions already in the therapist replies... Do NOT add advice, suggestions, questions, facts, numbers or links." The language instruction is repeated last (the model otherwise copies the examples' language).

Faithfulness guard (check_rephrase_faithful) - instant, no second model call:

  • non-empty;
  • no digits or URLs that the therapists did not write;
  • length ≤ 1.6× the combined therapist text (floor 40 chars);
  • ≥ 60% of the reworded text's content words appear in the therapist text.

The output is buffered (1-2 sentences) before the user sees anything. Fail → the therapist's original goes out. Honest limits: catches drift, padding, added numbers/links; does not prove semantic equivalence (a reword could shift meaning with the same words). For Hindi/Hinglish the word-overlap test is skipped (only empty/number/link checks). A judge-model or NLI check is the upgrade if quality demands it.

E7. Languages: Hindi, Hinglish, mixed

  • Why a translation layer: red flags, signals and the therapist library are English-only; a Hindi crisis message scored ~0.2 against them and was missed. So non-English text is translated in (Sarvam mayura:v1, mode modern-colloquial, ~0.7 s) and the whole pipeline runs on the English text.
  • Out: fixed replies (therapist reply, clarifying question, red-flag script, welcome) come from kb_translations, pre-translated offline (a few ms). LLM-written replies are produced directly in the user's language - no extra call, streaming kept.
  • Why mayura, not sarvam-translate: the latter turned "I got laid off yesterday aur mujhe lag raha hai ki main failure hoon" into "I felt depressed when I lost my job yesterday" - meaning lost.
  • Limits (state them): translation can soften an idiom - "kabhi kabhi lagta hai sab khatam kar du apni life" was translated too weakly and not escalated, so a clinician-approved Hindi/Hinglish crisis-word safety net on the original text is still recommended; machine-translated crisis scripts are marked reviewed=false pending native-speaker/clinician review; Sarvam is rate-limited (~100 calls/min on the current key), a production-capacity question.

Why it is built this way (expect these questions)

  • Why embeddings, not keywords? The doctors deliberately wrote disguised language ("if a car hit me I'd be okay with it"). Keywords miss paraphrase.
  • Why permissive thresholds? A false positive costs a moment of extra caution; a false negative is a missed danger signal. Safety fails upward.
  • Why a lower bar (0.36) for suicide flags? Live tests: explicit statements ("I want to kill myself", "I want to end my life") scored only ~0.39 - below the general 0.44 line - and the nearest flag overall was sometimes RF-020 with RF-018/019 right behind it. Fixed by checking those flags in the top 15 at 0.36. Ordinary messages ("I had a fight with my mom") score 0.19-0.29, well below.
  • Why a soft zone for RF-028 and RF-007? "I want to leave my partner" (no danger) scored 0.46-0.59 against RF-028 because every example phrase says "partner". RF-007 (exaggerated startle) fired on ordinary worry language at 0.39-0.44 while its genuine phrases score 0.50-0.69 - fixed 9 Oct at the product owner's instruction; a clinician should still confirm that a weaker real startle disclosure getting a gentle question is acceptable.
  • Hard rule enforced by a unit test: a suicide/self-harm flag can never be added to the soft zone.
  • Fail-safe, always upward: embedding failure or interlock failure → "I want to make sure you get the right support - let me connect you with someone" (localised). Never a silent continue.
Gaps to volunteer, not defend:
  • RF-028, RF-029, RF-030, RF-031 (suspected violence, history of violence, suspected rape, sexual molestation) have no approved script. Code sends them to a human-alert path - the app never improvises - but the client must write the four scripts. Top-priority ask.
  • No outbound human-alert integration yet. The turn's tier, interlock_triggered and requires_human_alert are recorded in the audit log, but the streaming endpoint returns plain text only; the notification to the main backend / on-call clinician is not built and needs the client's escalation contract (who is paged, how, how fast).
  • Hindi/Hinglish idioms can be softened by translation (Part E7); a clinician-approved crisis-word net is recommended.
  • RF-025's own trigger phrases include "slamming my fist in the wall", which makes it fire on anger at others; it is held to 0.50 as a stop-gap - the real fix is the doctors editing that phrase.
  • One vector per flag blends all phrases (Part C3); per-phrase vectors would likely separate better.

F7. Quick answers: "how does tier shifting happen?"

  • 1 → 2: score reaches 40 from new doctor-weighted signals plus confirmed duration/impact. Gradual.
  • 2 → "suggest a professional": only when the redirect gate clears (score ≥ 40 + duration + impact + ≥ 3 distinct signals).
  • 2 → 1: quiet turns subtract 5 each; the score can fall below 40.

  • Never: 2 → 3 by accumulating points. By design.

Why banded (strong / partial / none) specifically

The three failure modes are different. Very close: the best, safest, fastest answer is the therapist's own text - do not touch it. Close but not identical: the therapist's meaning is right but the wording needs to fit this person, which an LLM is good at if constrained (examples-only prompt + guard + fallback to the original). Nothing close: the honest answer is "I don't have an expert answer for this yet" - ask, don't guess, and only then use the LLM.

What the approach buys the product

  1. The LLM gets a narrow job ("reword these") that small models do reliably, instead of "be a therapist".
  2. Grounding in real expert language sets tone and content better than any persona paragraph.
  3. Errors are contained: safety is independent; a bad reword falls back to the original; an LLM outage still serves the therapist reply.
  4. Every reply is explainable (served_from + therapist_turn:<id>) - what makes clinical review and DPDP-style audit possible.
  5. A built-in improvement loop: every "none" is a gap for the therapists to fill; every approved row helps immediately.
  6. Latency and cost fall as the library grows - more strong matches means fewer LLM calls.

Earlier you said conversation files were 'style only'. Now you search them. Which is it?

It changed. The first design used them only to teach tone. Your requirement that replies come from your conversations when a similar one exists made them the primary reply source: each (user said → therapist replied) pair is stored, embedded on the user text, and searched on every turn.

H2. Ingestion

How does the ingestion pipeline work end to end?

Offline, one parser per file type. Parse along the file's own structure (rows, headings, 'User:/AI:' lines), clean and normalise, hold back unfinished or sensitive rows, embed only specific fields in batches of 64, store text and vector on the same Postgres row with an HNSW index, mark therapist rows unapproved until approved, pre-translate fixed replies, then spot-check with the real pipeline. Commands are idempotent, so re-running after a file changes is safe.

Why one row per chunk? Why not fixed-size or semantic chunking?

Your files are already segmented by clinicians - a sheet row, a heading section, a dialogue turn pair is a complete idea. Fixed-size chunking cuts ideas in half, and an LLM chunker adds cost and risk for no gain. We reserve an LLM boundary-refiner for future flowing prose, which has not arrived.

What exactly is embedded for each source?

Only the field that is real human phrasing: signal phrasings, symptom 'how users describe it', red-flag trigger phrases (joined, one vector per flag), pattern names, therapist user text, situation text for strategies, clarifying questions. Never rules, thresholds, scripts, or the clinical markers.

If they push: Why user text only for therapist rows? Because the next user message describes a situation; matching on the therapist's reply text would match the wrong thing.
How do you handle messy or unfinished source data?

Parse, normalise, and hold - never guess. Rows with placeholders like [technique], drafting notes, stray headings, under four words, crisis conversations and governance-held content are stored with a reason but never embedded, so no search can return them. Today 1,210 of 6,440 therapist rows are held. We also never invent content: 12 situations with no strategy stay empty.

Is ingestion repeatable? What if we send an updated file?

Yes. Each pair has a content hash, so re-ingestion upserts; if a parser fix changes a reply, stale rows from the re-parsed files are pruned. Approval flags survive a re-run unless you ask to reset them. To remove one bad reply: set approved=false on that row - instant, no deploy.

What real problems did ingestion find in our files?

Highlights: the red-flag Bot Script column had an em-dash in its header so a naive parser returned empty scripts for all 31 rows; the 'Career 500' file was one template repeated; sheet 17 has four sections plus an 84-row matrix, not three; PHSY typos; mixed ID formats; encoding in Windows-1252; ~100 therapist replies had scenario headings glued on; five documents are incomplete. Each was fixed or held and is documented.

Which embedding model do you use and why not Sarvam?

OpenAI text-embedding-3-small at 1024 dimensions. The architecture PDFs named Sarvam, but Sarvam has no embeddings API - we checked their live model list and reference. This is a vendor substitution that needs your written sign-off before real user data is embedded, along with confirmation that the vendor is on a no-training, no-retention tier.

If they push: Switching embedding models later means re-embedding everything and re-validating, so we should decide once.
What happens when we add new therapist conversations?

Drop the .docx in the source folder, dry-run to see held-row counts (unexpected holds mean a format issue), ingest, approve, pre-translate, then run a test message through the pipeline to see the source and similarity. It helps immediately - no training and no deploy.

How do you know ingestion is correct?

Parsers are unit-tested (50 tests overall), every file was inspected against its real structure first, and the dry-run reports held reasons. What we do not yet have is a full validation gate with a therapist-labelled test set measuring retrieval hit-rate and grounding accuracy separately. That needs your labelled messages.

H3. Signals and how the AI 'understands'

How do you detect signals in a user's message?

We embed the message once and compare it to the embedded phrasings of your 285 signals and the 'how users describe it' text of the symptoms. Matches at 0.45 similarity or above (top five each) become observed signals. No LLM is involved in recognition.

Isn't matching by similarity unreliable for clinical signals?

At the single-message level, yes, and we say so: a benign message once scored higher against 'Hypomania' than a genuine message did against its own signal. That is why one match never decides anything. Signals accumulate across the conversation, only new ones add points, a per-turn cap stops spikes, and the tier needs confirmed duration and impact.

How does the AI understand a signal once it is found?

The code understands it, using your data: severity 1-3, category, linked disorders, red-flag flag, linked symptoms and rules. The LLM never sees raw codes or diagnoses. It receives guidance such as 'naturally ask how long this has been going on' or your own 'when to keep probing' text for the nearest pattern.

What do EM and PHYS codes do?

PHYS rows (21) have real phrasings and map to signals. EM rows (133) are category labels - 'Life transitions', 'Intimacy concerns' - and they are exactly what the Tier 1 routing rules reference (e.g. EM45 to 54). We resolved an early belief that EM codes were missing: they were in the symptom sheet all along.

How do you read 'how long' and 'is it affecting life'?

A small separate LLM call asks two yes/no questions about the current message and must quote the exact words that justify each yes. It only runs while one of them is unconfirmed, and on any error it fails closed (treated as not confirmed). It reads the current message only, so something confirmed several turns ago and not repeated can be missed - a known limit.

Can the system recognise that someone is improving?

Partly. The score decays by 5 on quiet turns. Your 'graceful exit' trigger per pattern - the clinical definition of improvement - is stored but not yet wired, and resolved-past-struggle language ('I used to feel that way') is not specially recognised yet.

H4. Retrieval and the reply

How is the reply chosen?

Safety first. If safe, we search the therapist conversations by meaning. Best match ≥ 0.85 (0.90 if from mid-conversation) is sent as written with no LLM. 0.62 to 0.85: the LLM rewords using up to three close therapist examples, buffered and checked; on failure the therapist original is sent. Below 0.62: a therapist clarifying question if nothing else grounds the turn, else the LLM with grounding (Tier-1 self-care, doctor probing text).

Where does the LLM invent content, if anywhere?

On matched turns, nowhere by design: it may only reword the therapists' ideas, and an instant guard rejects added numbers, links, padding, or low word overlap. On unmatched turns the LLM does answer, but grounded in your self-care strategies or doctor guidance when available, and only after a therapist clarifying question has had its chance. That path has a log-only output check today; strengthening it is on the roadmap.

If they push: Be exact: 'we constrain and check', not 'the LLM can never say anything new'. The rewording guard is a drift detector, not a proof of equivalence.
What is the difference between strong and partial?

Strong means the user's message is near-identical in meaning to a situation a therapist already answered, so the therapist's reply is the best answer and we do not touch it. Partial means the topic is right but the wording differs, so the LLM adapts the therapist's meaning to this person, under the check.

Why are the thresholds 0.85 and 0.62?

Spot checks showed 'right topic, different words' lands around 0.64-0.66 and 'wrong topic' at or below ~0.56, so 0.62 sits in the gap. 0.85 for strong is deliberately conservative so verbatim use is rare until calibrated. They are provisional and environment-configurable. We will calibrate with your labelled set, target at least 95% precision on strong, and re-run whenever the library grows.

If they push: Do not claim they are validated. Say: 'educated starting points, calibration is the next major piece of work, and it needs your doctors.'
What stops a wrong therapist reply being sent?

Layers: the interlock runs first; only approved and match-eligible rows are searchable; very short or incomplete rows are held; mid-conversation replies need extra similarity; a clinically-sensitive topic can be held by a flag; and a bad row can be switched off instantly. The residual risk - a confidently wrong strong match - is exactly why thresholds need calibration and why the approved flag means 'included', not 'clinically reviewed'.

What if no conversation matches?

We prefer asking to guessing: a therapist-written generic clarifying question (limit one in a row, skipped for tiny messages like 'hi'). If something else grounds the turn - a self-care strategy or the doctors' probing text - the LLM answers with that. Every no-match is a real gap your therapists can fill by adding a conversation.

How do you avoid the same reply repeating?

We don't yet. A reply-variety layer is planned: vary only opening/closing connectors, never clinical content. It is not built.

How are the welcome messages chosen?

Random pick from your 23 approved openings; 'user' replaced with the person's name or 'there'. No LLM, no embedding, one small query - instant; there is a neutral fallback if the table is empty.

Is anything cached? Could caching skip safety?

Exact-match replies are cached in Redis for 24 hours (LLM replies only). Caching can never skip safety: triage, scoring and the interlock run on every turn even on a cache hit. The semantic cache is currently a stub.

Does the user's history affect replies?

Yes, within limits: the last six turns go into LLM prompts, the running score and observed signals persist for the session (six-hour inactivity TTL), and the candidate pattern sticks across turns. The long-term running summary is not built yet.

H5. Tiers and safety

How does the shift between Tier 1, 2 and 3 happen?

Three separate mechanisms. Tier 3 is only ever produced by the red-flag interlock, instantly, even on message one. Tier 1 to 2 is a 0-100 running score (Tier 2 at 40) built from doctor-weighted new signals (8 / 15 / 25 points by severity), +10 for confirmed duration, +10 for confirmed impact, -5 on quiet turns, capped at +25 per turn. Suggesting a professional is a third decision behind its own gate: Tier 2 plus duration plus impact plus at least three distinct signals.

Can a conversation climb into Tier 3?

No, by design. We had that bug in the first version - a work-stress chat reached '70+ = Tier 3' - and removed it. The score function can only return 1 or 2.

Where do the routing rules and sufficiency sheet fit?

Routing rules are evaluated every turn in priority order and logged; a Tier 1 result switches on self-care grounding. Tier 2/3 outcomes are not yet used to override the score because roughly 41 rules use range shorthand we cannot expand without your help, and we want your doctors to say how rule and score should combine. The sufficiency sheet supplies the nearest pattern and its 'keep probing' guidance.

When does the AI suggest booking or a professional?

Only when the redirect gate clears, and then as a gentle suggestion ('would you like help finding someone?'). Before that, at Tier 2, it keeps listening and naturally asks the missing duration or impact question and is told not to mention booking.

What does the system do for a suicidal message?

The interlock matches it (RF-018/019 checked in the top 15 at a lower 0.36 bar), returns the doctors' approved script word for word, records the flag and escalation target in the audit log, and never involves the LLM. On any internal failure it defaults to 'let me connect you with someone'.

If they push: State the gap: the outbound alert to a human is not wired to a destination yet - we need your escalation contract.
Why is the red-flag threshold so low? Won't it over-trigger?

Deliberately: a false positive costs a moment of caution, a false negative a missed danger. We kept it permissive and narrowed only where data proved a specific flag over-fires - RF-028 and RF-007 get a soft zone with a gentle follow-up; suicide flags never do, enforced by a unit test.

What about RF-028 to RF-031 with no scripts?

Code never improvises there: a match goes to a hard human-alert path. But it is a launch blocker on your side - we need the verbatim scripts and the alert recipient for violence, history of violence, suspected rape and molestation.

Does the interlock handle disguised or indirect language?

That is why we match by meaning. Your flags include disguised phrasing. Known limits: one blended vector per flag dilutes phrases, so explicit statements score lower than expected (hence the 0.36 bar for suicide flags), and indirect statements can fall short - we welcome more disguised example phrases from your clinicians per flag.

Hindi or Hinglish crisis messages?

Translated to English first (about 0.7 s), then the same interlock runs, and the script returns in the user's language from a pre-translated table. Residual risk: translation can soften an idiom, so we recommend a clinician-approved Hindi/Hinglish crisis-word list checked on the original text, plus native-speaker review of the translated crisis scripts.

What are Layers, and how do they relate to Tiers?

Independent dials: Tier is how serious; Layer is how deep the conversation has gone (rapport, explore, insight, action). A Layer-IV Tier-1 chat is very different from a Layer-I Tier-3 opening line. Only Tier is implemented today.

What happens in a stalled, contradictory, or disengaged conversation?

Sheet 17 defines it. The evaluation code and tests exist but are not yet connected to the live turn. It is a roadmap item and also needs the person's-name-to-role fix in three rows.

H6. Technical-team questions

What is the architecture?

Flutter and Next.js clients, a NestJS backend (auth, bookings), and this separate Python FastAPI AI service. The AI service uses one PostgreSQL with pgvector for text, rules and vectors, and Redis for session state and the exact cache. Providers (LLM, STT, TTS, embeddings, translation) sit behind interfaces, so a vendor swap is a one-line factory change. The AI service is deliberately isolated so a problem elsewhere cannot touch the safety checker.

What do you use for the LLM, speech and translation?

Sarvam for the LLM, STT, TTS and translation; OpenAI for embeddings; LiveKit for real-time voice. Deepgram was removed from the code. The architecture PDFs disagree on STT and avatar vendors; those remain client decisions.

Why pgvector and not Qdrant or Pinecone?

One system, one transaction, no sync problem, and the same query returns the vector neighbours and their text. At roughly 14,000 searchable rows an HNSW index returns in tens of milliseconds. We would revisit at millions of vectors.

What is the latency, and how do you protect it?

The target is 1.5-2.5 s from end of speech to start of response. Measured text-path totals were 0.45-0.93 s on strong and partial turns once the embedding call was warm (first call after idle spiked to ~3 s). The protections: one embedding per turn, the therapist lookup in the background, no judge-LLM, a rewording call that is small, and streaming. Embedding is nearly all of the time. Caveat: tiny sample, no p95 under load yet.

How do you scale?

The turn is stateless apart from Redis and Postgres, so the AI service scales horizontally. The main constraints are external: the OpenAI embedding call, and Sarvam translation which is rate-limited to about 100 calls a minute on the current key - a capacity question for production, since it only affects non-English turns.

How do you know why the AI said something?

Every turn writes an audit row: source (served_from), the therapist turn ids or chunk ids used, similarity, matched signals and rule, score and tier, redirect readiness, interlock flag, and per-stage timings. You can look up the exact therapist reply behind any turn. The audit never stores the user's raw text.

What about data protection and DPDP?

The agreement requires Indian data residency, encryption at rest and in transit, least-privilege access and retained audit logs; we should confirm in writing exactly where each vendor call (embeddings, LLM, translation) is processed. The contract (clause 5.7) forbids using client data to train models, so every vendor must be on a no-training, no-retention tier confirmed in writing, and a vendor change needs your written consent (clause 2.8). Open items we flag ourselves: the written sign-off for OpenAI embeddings and Sarvam translation, and the privacy design for any future gap-queue that would store user text.

If they push: Do not state specific hosting regions or certifications you cannot confirm; say you will confirm in writing.
How do you test this?

50 unit tests (parsers, banding, rewording guard, language, translation, soft-zone guard), live runs through the real pipeline with a dev tool, and EXPLAIN checks on the vector query. What is missing: the therapist-labelled evaluation set and a load test.

Is the matching using the HNSW index?

Yes - after we fixed a bug on 13 October. The filter was rendering as approved IS true, which Postgres cannot prove implies the partial index predicate, so it silently did a sequential scan. Using the bare boolean columns restored an Index Scan; the rule now is EXPLAIN after touching that query.

What if OpenAI or Sarvam is down?

Embedding failure gives the fail-safe message and an audit row - we never continue silently. On the partial path, an LLM failure sends the therapist's original text. A translation failure lets the turn continue on the original text with the English-only steps skipped. A quick embedding retry is on the roadmap.

Can we switch off the therapist-first behaviour?

Yes: CURATED_MATCH_ENABLED=false restores the pre-therapist-first behaviour exactly. All thresholds are environment variables, not code.
